Project: house_monitor (package, formerly a single house-monitor.py script)
Asyncio-based Python scraper that watches Austrian real-estate sites and emails notifications about new/cheaper listings.
Production location:

Package: /opt/house-monitor/house_monitor/ (see the "Package structure" section below)
Entry point: python3 -m house_monitor.main (ExecStart in the systemd unit)
Log: tail -f /var/log/house-monitor/service.log
Service: sudo systemctl status/restart house-monitor
DB: /opt/house-monitor/seen-houses.json

Important scraper-specific knowledge:

Goldgrube: decodes raw bytes with the decode_utf8_or_latin1() helper (house_monitor/models.py) — always tries UTF-8 first, because the server sometimes mislabels a response as iso-8859-1 when its bytes are actually UTF-8 (a plain latin-1 decode would accept this without error and produce mojibake, e.g. "GrÃ¼nen" instead of "Grünen")
Price parsing: as of 2026-07-02, all 18 text-based scrapers (every scraper except Bazar) read the German-formatted price (dot=thousands separator, comma=decimal) through the shared parse_de_price(text) helper (house_monitor/models.py) — previously this same regex+replace logic was repeated verbatim in ~11 places, now it's tested in one. Bazar is the sole exception: it casts the JSON API's numeric value directly (no text price string, doesn't need the helper). ImmoScout24 keeps its own card-narrowing logic (it has to pick the right one out of several price-looking `<li>` elements, excluding the `/m²` one) — but the final numeric normalization (dot/comma conversion, converting to float) is now delegated to the helper too; only the "which substring are we looking at" decision stayed custom. The previously documented 4 "historical leftovers" (Findheim, FindMyHome, Immi, Wohnnet) have been migrated — each was tested individually against edge cases before migrating (e.g. FindMyHome's "30.000,-" trailing-dash format), the 68 tests stayed green afterward.
Willhaben: reads from the __NEXT_DATA__ JSON. `PRICE` is always the TOTAL price (willhaben carries the per-m² price in separate `PRICE/SQUARE_METER…` attributes; `PRICE_FOR_DISPLAY` reads "€ 19.000"), so an ad is skipped as per-m² only if its `PRICE_FOR_DISPLAY` explicitly says "/m²". 2026-10-09 fix: the former guess "price × area > EUR_PRICE_TO ⇒ per-m² price" dropped nearly every real ad that states its area (149 in one run — e.g. a 19 000 € / 20 m² holiday hut); the source returned ~15 listings a day instead of ~190. A survey of all 236 in-range adverts found no per-m² PRICE at all.
Findheim: the server-side price filter is unreliable → client-side safety filter in the main loop. 2026-07-01: the site got a Tailwind redesign, the old card selector (div.group + "rounded-md") and price container (div.z-[1]/right-0/bottom-0) stopped working, which caused it to silently return 0 results for MONTHS (even though real, in-range listings existed). Fixed: card = div.group + "overflow-hidden" + "border" in the class list; price = the `<p class="font-semibold ...">€ X</p>` next to the title. Lesson: a scraper returning "0 listings" does NOT automatically mean there's no inventory — it has to be checked live (without the card-count filter, then with price parsing), because a site redesign can just as easily silently break the selectors.
DerStandard: the search page's card markup changed around 2026-10-21 — the card's link used to be a separate `a.sc-listing-card-content-background-link`, the title a `div` and the price a `ResultItemPrice` span; now the title is an `h2.sc-listing-card-title` whose `a.sc-listing-card-title-stretched-link` holds the /detail/<id> link, and the price is the footer's `div.sc-listing-card-footer-item-main` (desktop view; the `PropertyPrice…propertyPrice` span next to the address, the mobile view, as a fallback — the footer's other items hold the area and rooms, hence the "main" class). The cards were still there, but every one was dropped for its missing link: 0 listings from 10-21 on, and the 10-22 end-of-day check flagged `source:DerStandard` (day 1). Nothing was lost: on 10-23 the fixed scraper's 38 in-range listings were all known, blacklisted or copies of ads other portals had brought. Pagination (&page=N, HTTP 404 past the last page), the address span (now "1220 Wien , Street") and the ds_<id> ids are unchanged.

Its feed escapes a numeric entity that has lost its "#" ("&amp;8364;" in the page = "&8364;" after parsing, for "€"); `_parse_cards` restores the "#" before unescaping — before 2026-10-10 the titles (and the emails) showed the raw "&8364;"

HegerReal (hegerreal.at): a broker site backed by the Justimmo real-estate CMS (justimmo.at storage/thumb URLs give it away). The whole inventory (houses, apartments AND rentals) sits on ONE paginated list (/aktuelle-immobilien) with no server-side price/type filter, so filtering is fully client-side (like Sonnberger/Findheim). Card: div.realty-wrapper; title/URL: h3 > a (relative href /objekt/<id>?from=... → made absolute for the email link); ID: the numeric /objekt/<id> (heger_<id>). Price: the short-info <li> whose `.list-item-desc` label == "Kaufpreis", read from its sibling `.list-item-value` — the label check is REQUIRED because another <li> in the same list holds the area ("Fläche ca. 65,38 m²"), which an unscoped parse_de_price would grab instead (same class of pitfall as ImmoScout24's /m² li). Rentals carry a "Miete" (rent) row instead of "Kaufpreis", and already-sold listings ("erfolgreich vermittelt YYYY") have no price row at all → both parse to 0.0 and are dropped by the existing price==0 filter, no special-casing needed. Pagination: page 1 = /aktuelle-immobilien, page N = /aktuelle-immobilien/p/N; past the last page the server returns HTTP 200 with 0 cards (no 404). 2026-09-17 live check: 3 pages / 40 listings, 2 genuinely in-range (two Mobilheime at 25k/50k € — real inventory exists in-band, this isn't a theoretical scraper).

**Parallelizing scraper runs:**
- The 22 scrapers run concurrently in run() via `asyncio.gather(*(s.fetch_listings() for s in scrapers), return_exceptions=True)` (previously they ran strictly sequentially, one after another, which needlessly slowed down the whole run even though the scrapers hit independent domains and share no state besides the common aiohttp.ClientSession)
- Because of `return_exceptions=True`, a scraper raising an exception doesn't sink the whole run — only that one source is skipped (and logged), the rest continue undisturbed
- For scrapers that crawl multiple independent base URLs (OhneMakler: 2, Immokralle: 2), fetch_listings() is split into a `_fetch_one_url(base_url)` helper method, which is also called per-URL concurrently via `asyncio.gather`; the results are then merged afterward with a single shared `seen_ids` set, so any overlap (duplicate ID) between base URLs doesn't end up twice in the final result

**Connection-drop retry + same-day retry of failed sources (2026-07-13):**
- Root cause of the recurring `[Errno 32] Broken pipe` (daily on Findheim page 2, occasionally Raiffeisen/Willhaben): the shared session's keep-alive pool hands out a socket the server already closed while a slow page was being processed — the next pagination request writes into the dead connection. On 2026-07-12 it hit Findheim's page 1 → "Findheim: 0 listings" for that run (selectors were fine, verified live).
- First line of defense: `fetch_text(session, url)` (house_monitor/fetch.py) — GET returning `(status, body)`, retries `aiohttp.ClientConnectionError` (covers ClientOSError/broken pipe AND ServerDisconnectedError) up to 3 attempts with 2s/4s backoff; the retry runs on a fresh connection (aiohttp evicts the broken socket), so one retry almost always succeeds. Deliberately NOT retried: non-200 statuses (callers' own status handling stays in charge) and timeouts (retrying those at the 16:00 concurrent peak would only slow the run). Currently used by the 4 scrapers with observed failures (Findheim, Raiffeisen, Willhaben; Goldgrube since 2026-07-13 after a live "Server disconnected" hit — it uses the `fetch_bytes` sibling helper, which returns (status, raw bytes, declared charset) untouched so `decode_utf8_or_latin1` stays in charge of decoding; plain fetch_text would re-introduce the mojibake bug) — migrate others individually if they start failing too, same as the parse_de_price migration pattern.
- Second line: same-day source-level retry. Every scraper (all 21 since 2026-10-09 — before that only the 4 above, so sources that timed out at the 16:00 concurrent peak, e.g. Propylo/Immobilien.de/Dibeo, were silently skipped until the next day) resets `self.incomplete = False` at the start of fetch_listings() and sets it to True when the fetch ends on an error — an exception such as a timeout or dropped connection, NOT a non-200 status, which stays the caller's own break logic (partial results are still returned and processed). Multi-URL scrapers set it from `_fetch_one_url`; Immokralle sets it when its urllib helper returns None. The old run() body is now `_scrape_and_notify(scrapers) -> failed_scrapers` (returns gather-level crashers + `incomplete`-flagged ones, via `getattr(scraper, "incomplete", False)` — scrapers without the flag work unchanged). The main loop then retries ONLY the failed sources after `INCOMPLETE_RETRY_DELAYS = (1800, 1800, 3600)` (config.py) — the main 16:00 email is never delayed; anything new found on retry goes out as a separate follow-up email the same day; the seen-DB + cross-platform dup filter prevent double-notification.

**Daily error checks — the "HIBÁK" section of the 16:00 email (2026-10-09, house_monitor/health.py):**
- Why: a site redesign breaks a scraper silently — it just returns 0 forever (Findheim 2026-07). A plain "0 results for N days" rule doesn't work here, because the search URLs carry 3000–70000 € server-side, so a working source can be legitimately empty for weeks (OhneMakler) and would alert daily.
- When: once a day in run(), after the 16:00 run AND its same-day retries (`_end_of_day_check(scrapers, still_failed)`). `self.day_counts` (scraper class → listings from its latest fetch; a retry overwrites the main run's count) is filled by `_scrape_and_notify`.
- Broken today = the day's count is 0 AND (the source was still failing after all retries — e.g. a site that times out all day — OR its `probe()` fails after `HEALTH_PROBE_ATTEMPTS`=3 tries 5 s apart OR the probe page has no card with price > 0). A source with results, or with 0 results but a healthy probe ("nothing in range"), is OK and resets its streak.
- `probe()` (every scraper): page 1 of the same search WITHOUT the price range (`*_PROBE_URL` / `BAZAR_PROBE_PARAMS` / `IMMOLIVE24_PROBE_DATA` in config.py; Goldgrube/Sonnberger/HegerReal reuse their unfiltered URL), parsed by the scraper's own `_parse_cards`/`_parse_items`/`_parse_json_adverts` — no duplicated selectors, so the probe can't drift from the scraper. Errors and non-200s propagate (fetch_page raises HTTPStatusError) — an error must never look like an empty page. Counting cards with price > 0, not raw cards, is deliberate: ImmoScout24 finds its cards but reads no price from any of them, which a raw-card rule would miss. Two probe targets deviate from "same search minus price": Bazar keeps `price.from` (ascending without it, page 1 is all 0 € ads) and Wohnnet uses the default sort (its cheapest-first page 1 is entirely German listings, which `_parse_cards` skips by design — on 2026-10-09, 202 of the 220 in-range cards were German and all 17 Austrian ones were parsed, so the scraper itself is fine).
- Silent PARTIAL losses (sources that do return results; `_source_findings_without_probe`, no extra request): (1) `drop:<name>` — today's count < HEALTH_DROP_RATIO (0.4) × the median of the source's previous HEALTH_DROP_WINDOW (14) daily counts, needing HEALTH_DROP_MIN_HISTORY (7) days and a median ≥ HEALTH_DROP_MIN_MEDIAN (5); calibrated by replaying the Aug 1–Oct 9 2026 daily counts from service.log: it would have caught the ImmoScout24 breakage 3 days in (08-27) and a 3-day FindMyHome outage (09-20..22) with no false alarm (a 0.5 ratio added two). The per-source `count_history` lives in the state file; a source already flagged `source:` (broken outright) gets no `drop:` on top. (2) `coverage:<name>` — sources whose site reports its own total set `scraper.coverage = (items received, site total)` after a complete fetch: Dibeo (`totalElements`), Lystio (`paging.cardCount` — not totalCount, a project card groups units), Immobilien.de (`total`, requested with `count: true`), Willhaben (`rowsFound` per search, summed); fewer than HEALTH_COVERAGE_MIN_RATIO (0.8) × the total received → missing pages. (3) `late:<name>` — a source that failed at 16:00 and only came through a same-day retry (`day_late`), i.e. its listings arrive late in a follow-up email.
- The monitor's OWN errors of the day are counted the same way: `self.today_errors` (kind → Hungarian detail) collects `email_send` (`notifier.send` returned False), `db_save` (`_save_db` raised), `run_crash` (the daily cycle raised — run() now catches it, logs it and waits for the next day instead of dying; before, systemd restarted the process and the day was lost silently) and `health_check` (the start/end-of-day bookkeeping itself raised); labels in `INTERNAL_ERROR_LABELS`.
- Streaks: `_end_of_day_check` turns every finding into a key (`source:<display name>`, `internal:<kind>`) and `update_streaks` counts CONSECUTIVE DAYS (continues only if the key was also found yesterday; anything not found today drops out = recovered). `due_alerts` = streaks of `HEALTH_MIN_CONSECUTIVE`=2+ days — the owner's rule: every error class is reported only once it has lasted 2 days. They're stored as `pending_alerts`.
- Reporting (the owner's rules): NO separate alert email — `_daily_run` → `_start_of_day()` returns the pending alerts (plus a missed-run notice, below) and `_scrape_and_notify(scrapers, alerts=…)` appends `build_alert_section()` ("HIBÁK — legalább 2 napja fennállnak…", one line per alert with its day count) to the 16:00 listing email; with no new listing an errors-only email still goes out. The subject names "hiba" whenever errors are in it (`email_subject`: "Ingatlanok: N db", "Ingatlanok: N db + K hiba", "Ingatlanok: K hiba"). Pending alerts are cleared only once that email was actually sent, then recomputed at the end of the day — so a lasting problem shows up EVERY day (the owner's explicit choice), with no recovery email. A finding from the end of day N reaches the email of day N+1 at 16:00; the retry follow-up emails never carry alerts.
- Missed runs: `_start_of_day` compares `last_run_date` with today; 2+ whole days without a 16:00 run (Pi down, /opt still locked after a reboot, service stopped) → a "Kimaradt futás" alert in the first email after it runs again. A monitor that doesn't run at all can't report anything — the owner declined a weekly heartbeat email.
- State: `health-check-state.json` next to the seen-DB (gitignored): `last_run_date`, `last_check_date`, `streaks` ({key: {days, last, reason}}), `pending_alerts`, `missed_runs` (until sent), `count_history` ({display name: last 14 daily counts}); atomic write. `last_check_date` makes a second end-of-day check on the same day a no-op (otherwise one bad day restarted twice would count as two "consecutive" days). Missing/corrupt file → {} (worst case: an alert one day late, never a false one). Every step is wrapped in try/except: the checks can never take the monitor loop down.
- First live run (2026-10-09, all 21 forced to "0 today"): only ImmoScout24 (15 cards, 0 prices — the PriceKeyFacts selector is dead) and Immobilien.de (0 cards — the site was rebuilt on Next.js, `a.lr-card` is gone and the Austria/price query params are ignored; rewritten the same day, see its paragraph above) were flagged; the other 19 probes found priced listings. ImmoScout24 fixed the same day: the price facts are now `<li class="PriceKeyFact-price-key-fact-…">` without the old `<ul class="PriceKeyFacts…">` parent, so the scraper had dropped every card as price=0 since ~2026-08-24 (the last is24_ last_seen); `_parse_cards` accepts both markups. Live after the fix: 52 listings, 10 000–70 000 €, and 0 would be emailed as new (the IS24 family shares the 24-hex expose id with Immodirekt/Immobilien.net, which kept covering them).

**The 16:00 first-wave timeouts (first diagnosed 2026-10-09, root cause found 2026-10-12):**
- Every day since at least 2026-09-01 a burst of TimeoutErrors hit the FIRST requests of the 16:00 run all at once, 30–40 s after the start (OhneMakler and Immobilien.de nearly daily, Propylo's 9 regions every day since it went live, Dibeo/Findheim/others sometimes) — 4–6 a day before Propylo, 12–17 after. The very same concurrent run of all sources at 17:15 in a fresh process had zero timeouts (Propylo: 318 listings in 24 s). Evidence for the cause: the service idles 24 h between runs, its memory gets swapped out (10 GB /swapfile, swappiness 60, page cache 6 GB of 7.8 GB RAM), and `sar -W` showed swap-ins jumping to ~54 pages/s in 16:00–16:10 from ~5 before — the process pages back in while its first requests' 30 s timers run. Same-day retries (16:30, warm process) rescue the sources; a `late:` finding reports a source that keeps needing them.
- Root cause (2026-10-12): the systemd unit (`/etc/systemd/system/house-monitor.service`, not in the repo) has `CPUQuota=20%` (the unit file was last changed on 2026-07-03) — cgroup `cpu.max` 20000/100000, i.e. 20 ms of CPU per 100 ms. The concurrent first wave needs ~11 s of CPU in its first 40 s (BeautifulSoup parsing of 0.5–1.5 MB pages — Findheim, Immodirekt, DerStandard —, TLS, gzip), which the quota stretches about fivefold: the event loop is blocked for 58 of the first 60 s (single stalls up to 10 s), so the requests whose responses get read last — Propylo's 9 — hit their 30 s total timeout; Lystio's "Broken pipe" and Wohnnet's timeout at 16:00 on 10-12 were the same starvation. Telltale: during a run the log timestamps fall on a 100 ms grid (the CFS period). Replay on the Pi with the production code under `systemd-run --user --scope -p CPUQuota=…`: 20% → all 9 Propylo regions TimeoutError at ~33 s, exactly like the 10-11 run; 100% → all 22 sources complete (Propylo 301 listings in 22 s), longest loop stall 1.6 s; no quota → the same. The 10-12 16:00 run itself used 21 s of CPU and was throttled in 988 of 1154 periods (78 s in total). The manual 17:15 run of 10-09 had no timeouts because it ran outside the unit's cgroup.
- Swap is real but secondary: on 10-11 (24 h idle) the run started at VmRSS=15 MB / VmSwap=58 MB and every Propylo region plus Findheim timed out; on 10-10 and 10-12 (fresh process, VmSwap=0) the quota alone still caused timeouts. `_daily_run` keeps logging "Process memory at run start: VmRSS=…, VmSwap=…" (`_memory_snapshot`, from /proc/self/status).
- Fix (system config, outside the repo): the `CPUQuota=20%` line was removed from the unit after the 10-12 diagnosis (`systemctl show house-monitor -p CPUQuotaPerSecUSec` → infinity). The monitor is a single asyncio thread, so it can't use more than one of the Pi's four cores anyway; `sudo systemctl set-property house-monitor CPUQuota=100%` would be the way to pin it to exactly that. Result: the 16:00 runs of 2026-10-13 to 10-16 had no TimeoutError at all, even at VmSwap=176 MB after four days of uptime — the swap alone doesn't cause the first-wave timeouts.

**Logging — the NOTICE level (compressing the console for manual runs):**
- `NOTICE = 25` is a custom log level (between INFO=20 and WARNING=30), used via the `log_notice()` helper
- On a manual run (not systemd), the console handler only prints NOTICE+ (milestones: run start/end, DB loaded, total result count, per-scraper summary, email outcome); the detailed per-page/per-listing INFO logs only go to the file (house-monitor.log)
- Console format on a manual run: `%H:%M message` (e.g. `19:12 Searching...`) — no date, seconds, or level name; the file/systemd log format is unchanged (full date+time+level, for debugging)
- The "Logging initialized..." line now goes through plain `logging.info()` (not `log_notice()`), so it doesn't show up on the console, only in the file
- Per-scraper summary lines in a compact format: `{Source}: {N} listings` or `{Source}: {N} ads` (the source name without the domain suffix, e.g. "FindMyHome" not "FindMyHome.at" — except where the TLD is the distinguishing part: Immobilien.net vs Immobilien.de)
- Unchanged in systemd mode (INVOCATION_ID env var): there's a single stdout stream, every INFO detail stays in it — it ends up in service.log, which CLAUDE.md documents as the place to debug from, so full detail is kept there

**DB reliability (seen-houses.json):**
- _load_db(): loads entries line by line, a single corrupt/incompatible entry is just skipped (and logged), it doesn't throw out the whole DB — previously a single bad entry would have taken down the entire thing, which would have caused a flood of duplicate-email spam (every already-seen house would have looked "new")
- _save_db(): atomic write — writes to `seen-houses.json.tmp` first, then renames it to the final name with `os.replace()`, so an interrupted write (power loss, kill) can't corrupt or empty out the existing database

- 2026-07-02: every one of the 19 scrapers' card-parsing logic was pulled out into a standalone, network-free-testable `_parse_cards(html_text)` method (`_parse_items`/`_parse_json_adverts` for the JSON-based scrapers) — previously only 5 scrapers (ImmobIlienNet, Immokralle, ImmoLive24, DingDong, Sonnberger) had one, the rest had their card processing embedded directly in the paginating `fetch_listings()`/`_fetch_one_url()` loop. `_parse_cards` only does the raw extraction (a list of id/title/url/price tuples — plus the card's address as a 5th element for the six SITE_BLACKLIST sources); dedup (`seen_ids`) and price-range filtering stay on the caller's side (fetch_listings) — this pattern was already the precedent set by the 5 pre-existing scrapers.
- IMPORTANT LIMITATION: the tests run against hand-built, static HTML/JSON fixtures, with no real network calls — this means the test suite CANNOT by itself catch a live site redesign (like Findheim's 2026-07-01 case above), it only prevents a regression of an already-known, already-fixed bug. A live check (card count/price parsing via a manual run) is needed if a source suspiciously returns 0 results.
- `scripts/live_smoke_check.py` (2026-07-02): a live-check script written in response to the limitation above — `python3 -m scripts.live_smoke_check` runs all 22 scrapers against the live sites, with no price/blacklist filtering and no email/DB writes, printing the result count per source (flagging 0-result/errored sources). Deliberately NOT part of pytest (network-dependent, slow, non-deterministic) — a manual/periodic diagnostic tool. The session has to send the SAME browser headers (User-Agent, Accept, Accept-Language) as the real `monitor.py` — without them, several sites (ImmoScout24, Immodirekt, Immobilien.net — all the same ImmoScout24 AT portal) block with HTTP 401, which would give a false "broken" signal.
- 2026-07-02: the first run flagged 6 sources as suspicious; on investigation, all 6 turned out to have no real bug. The 3 HTTP 401s (ImmoScout24, Immodirekt, Immobilien.net) were the script's own fault (missing headers, see above), not a site issue. The other 3 (OhneMakler, Immobilien.de, ImmoLive24) returned HTTP 200 with 0 cards — confirmed via manual curl with a raised price ceiling (100k/150k/300k) that the selectors/search parameters work correctly, there just genuinely was no house between 3000-70000 € on any of those sites at that moment (OhneMakler: explicitly empty GeoJSON; Immobilien.de: a "keine Treffer gefunden" ["no results found"] message on the page; ImmoLive24: the POST-based price filter scales correctly, it just genuinely returns 0 under 70k). Lesson: "0 results" alone really isn't enough to declare something broken — always confirm with a raised price ceiling/wider filter before calling a scraper "broken."
- Dev tooling (formatting/lint/type-checking, NOT needed to run the scraper itself): `requirements-dev.txt` (black, ruff, mypy, types-beautifulsoup4), configured in `pyproject.toml`. The `[tool.mypy.overrides]` section deliberately disables a few error codes (`union-attr`, `index`, `operator`, `call-arg`, `arg-type`, `assignment`) for the `house_monitor.scrapers.*` modules — this is noise from BeautifulSoup's imprecise types (e.g. `str | list[str] | None`), not a real bug; the root `house_monitor/` modules (monitor.py, email_notifier.py, etc.) run under full strictness.
- Dependabot (`.github/dependabot.yml`, added 2026-07-02) opens weekly PRs for outdated pip packages and GitHub Actions versions. A green CI run on a Dependabot PR only proves the network-free unit tests still pass — it does NOT prove the real scrapers still work, since aiohttp/bs4/lxml version bumps can change real network/parsing behavior that no unit test exercises. 2026-07-02 incident: the `aiohttp` 3.9.1 → 3.14.1 PR had green CI, but running `scripts/live_smoke_check.py` against it repeatedly produced `ClientPayloadError` on a different subset of scrapers each run (Findheim, Wohnnet, Raiffeisen, ImmoLive24, Immobilien.de) — a concurrency-related regression under this project's `asyncio.gather`-on-one-shared-session usage pattern. Reverting to aiohttp==3.9.1 reproduced zero errors across repeated runs. Rule going forward: any aiohttp/bs4/lxml Dependabot PR needs a `scripts/live_smoke_check.py` run against the live sites (ideally 2+ times, since this failure mode is intermittent) before merging, not just a green CI check.
